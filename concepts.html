Concepts

How a request flows through the proxy, what the compatibility limits are, and what the routing settings actually do.

How a request flows

Multi LLM sits between your tool and the provider. Nothing leaves your machine except the request itself, and only to the provider you selected.

  1. Your tool sends a request

    Standard OpenAI shape, to http://localhost:5000/v1/chat/completions with your local key. From Multi LLM's point of view it looks the same as any other client.

  2. The model name is resolved

    If it is a real model id, that model is used. If it is a virtual model such as multillm, the routing strategy picks a concrete one from its bundle.

  3. Health and circuit breakers are checked

    Providers with an open circuit breaker are skipped. If the chosen provider fails, the request fails over to the next candidate until the failover budget runs out.

  4. The prompt is compressed

    If token compression is on, filler is removed before the request goes out. Code blocks, JSON and fenced sections are never touched — see compression.

  5. The request is translated

    OpenAI shape becomes whatever the target provider speaks — Anthropic messages, Gemini contents, and so on. The reverse happens on the way back.

  6. The response is measured

    Tokens, latency and success land in the usage panel. A cache hit costs nothing and is not forwarded.

Your provider key never leaves

Multi LLM holds the key, uses it for the upstream call, and returns only the model's answer. The tool never sees it.

OpenAI compatibility

Multi LLM relays the standard OpenAI surfaces. Anything outside that list is refused rather than passed through blindly, so a typo cannot turn into an unexpected request to a provider.

Format translation

Your tool only ever speaks OpenAI. Multi LLM converts to the target provider's own shape and back. That is why an Anthropic model appears to a VS Code extension like any other model.

Two consequences worth knowing:

  • Provider-specific parameters pass through only where they exist. A parameter Anthropic does not understand is dropped rather than causing an error.
  • Tool calling is translated per provider. The tool schema is kept intact; the calling convention differs and is converted for you.

What is not supported

  • Fine-tuned model management — configure those at the provider.
  • Batch endpoints, which run jobs asynchronously upstream.
  • Anything not in the table above.

Unknown paths return 404 with a message naming the refused path, rather than being forwarded somewhere unexpected.

Streaming

Set "stream": true and the answer arrives token by token. The chunk format is the OpenAI one, whatever the provider actually does internally.

What changes between providers

Streaming is where provider differences show up most, because every provider invented its own event shape:

  • OpenAI-style providers emit incremental delta chunks.
  • Anthropic emits typed events and content blocks that get built up rather than appended.
  • Some providers send keep-alive or usage-only chunks with no content.

Multi LLM normalises all of that into one stream your tool can read. The cost is a small delay on the first token for providers that do not stream natively — the proxy buffers until it has something to send.

If a stream cuts off mid-sentence

Compare with streaming disabled. If it works that way, the tool does not handle the provider's keep-alive chunks. Report it with the provider name — the workaround is to turn streaming off for that tool.

Streaming and the cache

Only non-streaming requests are cached. Streaming is a one-shot interaction, and replaying a recorded stream would look like a hang.

Tokens and context

Prompt tokens

Everything in messages counts: system prompts, history, tool definitions and the current user message. A long conversation grows the prompt every turn, which is usually where the cost goes.

Completion tokens

What the model generated. Controlled by max_tokens and temperature — a high maximum does not cost more if the model stops early.

Context length

Each model has a limit, shown in the model card as 128K and similar. Exceeding it returns a provider error; the proxy does not silently truncate, because a truncated conversation produces a wrong answer that looks like a working one.

Where the numbers come from

Providers report usage in the response, and Multi LLM records that. When a provider returns nothing, the count is estimated and marked as such in the usage panel. Estimated numbers are close but not billing numbers — your provider's dashboard is authoritative.

Cost control

Two levers do most of the work: token compression shrinks the prompt before it leaves, and the usage ranking shows which model or provider actually costs you. See cutting token costs.

Quality signals

Multi LLM measures latency and availability, and it shows both per provider. It cannot tell you which model is better — that depends entirely on your task.

The health dot

DotMeaning
GreenProbed within the last 15 minutes, responding
YellowNo recent probe, or never checked — the last known state, possibly stale
RedFailing, or the circuit breaker is open

Probes run against the provider's own model list. They are cheap and periodic, not on every request.

Latency

Measured in milliseconds per request, averaged over a rolling window. It is the metric the latency and fastest routing strategies pick on. Averages hide outliers; the strategies work on the average, so a provider with occasional very slow calls can still be chosen.

Choosing a strategy

If you do not know where to start:

  • weighted is the default and a reasonable choice. Starred models get picked four times as often, so you can steer it by starring.
  • fastest if you care about response time more than consistent quality.
  • priority if you have a clear favourite provider and want it first, with the rest as fallback.
  • sticky for multi-turn work: the same conversation stays on one model, which usually reads better.

Why routing matters

A single model name per request means you commit to one provider for every task. Routing turns that into a bundle that adapts.

Virtual models

A virtual model is a named group of real models plus a strategy. Asking for multillm asks the strategy, not a specific provider.

Two things fall out of this. Failover happens without you noticing, because a failing provider is simply not chosen. And you can change strategy later without changing a single line in your tool.

Starred models

Starring a model multiplies its selection weight by four under weighted. It is a blunt instrument for steering traffic towards what works, not a ranking.

The built-in bundle

multillm exists from the first start. It contains every enabled model and uses weighted. You can edit it, rename it, or make your own — see virtual models.

What stays where

Worth being precise about, since the whole point of a local proxy is that data does not travel.

WhatWhere it goes
Your prompts and the model's answersTo the provider you chose, and nowhere else
Provider API keysYour local profile, compared as hashes, never sent to a tool
Usage historyYour local profile, per user
Your tool's local keyStays between the tool and the proxy; the proxy never logs it
Update checkOne request to GitHub for a version file, no identifying data

Multi LLM has no account, no telemetry and no analytics. The only network traffic is your request to the provider, and the optional update check you can switch off in Settings › App.

Glossary

Provider
One configured service with a base URL, a key and a list of models. OpenAI, Anthropic, Ollama and 90 others are all providers.
Virtual model
A named bundle of real models plus a routing strategy. Asking for it asks the strategy which model to use.
Routing strategy
The rule that picks a model from a bundle: weighted, round_robin, priority, latency, fastest or sticky.
Health check
A periodic probe against a provider to see whether it answers. Produces the coloured dot on the provider card.
Circuit breaker
After repeated failures a provider is taken out of rotation for a cooldown, then probed back in. Prevents every request from retrying a provider that is down.
Failover
Retrying a failed request on the next candidate model instead of returning the error. Bounded by a budget so it cannot loop.
Token compression
Removing filler words from a prompt before sending it. Never touches code, JSON or fenced blocks.
Response cache
Serving an identical non-streaming request from a local store instead of forwarding it. Bounded size and time-to-live.
Local key
The key your tool uses to talk to Multi LLM. Unrelated to provider keys and never passed on.
Expose to LAN
Listening on all interfaces instead of localhost only, so other machines can reach the proxy. Not for untrusted networks.
Token
The unit providers bill by. Roughly four characters of English, but the exact rule is the provider's.
