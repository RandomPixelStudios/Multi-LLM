Container

Docker

Run Multi LLM in a container in multi-user mode: setup, network, backup and hardening.

Why the container

The desktop app is one user on one machine. The container runs the same software in multi-user mode: one port, several accounts, each with its own providers, models, keys, usage history and personal port.

When to use it

  • A team, especially one that is not all in the same room.
  • A server you want running whether or not someone is logged in.
  • Any setup where you would otherwise hand around one provider key.

What it does not have

No desktop window. The tray icon needs a desktop session. Everything is managed through the web interface at http://localhost:5000.

A desktop app still exists

The container is one deployment option, not a replacement. Most solo users never need it.

Prerequisites

  • Docker Engine with the Compose plugin. Nothing else: no Node, no Rust, no compilers.
  • The repository, because the image is built from source.
  • Host port 5000 free.
  • A provider key, or a local engine reachable from the container.

Check your setup

docker --version docker compose version

Both must answer. On Linux you may need to add yourself to the docker group to avoid sudo on every command.

Quick start

git clone -b Docker https://github.com/RandomPixelStudios/Multi-LLM.git cd Multi-LLM/docker docker compose up --build -d docker compose ps # "healthy" once the port is bound

Open http://localhost:5000. The first account you create becomes the admin.

From another machine

http://192.168.1.50:5000

Your host's LAN address, not localhost. See network and firewall.

It does not start on reboot

By design. After a restart, start it yourself:

docker compose start

See commands for the full set.

The compose file

Two files sit next to each other in docker/. The compose file points at both, so the layout looks more spread out than it is.

services: multillm: build: context: .. # the repository root, because the build needs the source dockerfile: docker/Dockerfile image: multillm:latest container_name: multillm ports: - "5000:5000" volumes: - multillm-data:/data environment: MULTI_LLM_DATA_DIR: /data MULTI_LLM_PORT: "5000" MULTI_LLM_EXPOSE: "1" MULTI_LLM_SERVER: "1" restart: "no" volumes: multillm-data:
LineWhy it is there
context: ..The image builds the frontend and the Rust binary, so it needs the whole repository.
MULTI_LLM_EXPOSE: "1"Binds all interfaces, so the team can reach it. Remove it for localhost only.
MULTI_LLM_SERVER: "1"Multi-user mode: separate profiles, per-user keys and ports.
restart: "no"Deliberate. Nothing starts after a reboot without you asking.

Users and keys

Creating accounts

Two ways, both valid:

  • At first start, from the login screen — the first account is the admin.
  • Later, from the Users tab, visible to the admin only.

Only a username and a password. No e-mail, no external login, no verification step.

What each user gets

IsolatedShared
Providers and their keysThe container and its port
Models and virtual modelsImage and version
API key, created automatically, never changesResource limits
Usage history and costsThe user list, for the admin
A personal port from 8123 upward

Getting a user's key

./multillm/get-key.sh anna

Prints that user's local API key, ready to paste into a tool. The key never changes, so a tool configured once keeps working.

How requests are attributed

Every /v1/* request is matched to a user by the key in the header. That is how several people share one port without seeing each other's usage.

Stopping sign-ups once you have accounts

Leave MULTI_LLM_ALLOW_SIGNUP unset. Otherwise anyone who reaches the port can create an account.

Data and volumes

Everything lives in the named volume multillm-data, mounted at /data:

/data/ users/ anna/ settings, providers, keys, usage bernd/ the same, isolated ...

The volume survives updates and rebuilds. That is the whole point of using a named volume rather than a bind mount into the source tree.

API keys are in there, in plain storage

Provider keys live in the volume. Anyone with read access to the Docker socket effectively has them. See security.

Updating

cd Multi-LLM git pull cd docker docker compose up --build -d

Only a rebuild is needed. The volume keeps all data, so users, keys and usage history survive.

Before a bigger jump

Back up the volume first — see backup and restore. Beta releases can change the settings format.

Command reference

docker compose up --build -d # build and start in the background docker compose ps # status; "healthy" once the port is bound docker compose start # start docker compose stop # stop, keep everything docker compose down # stop and remove the container, data stays docker compose down -v # ALSO remove the data volume - destructive docker compose logs -f # follow the log docker compose restart # restart
down -v cannot be undone

It deletes accounts, provider keys and usage history. Take a backup first if any of that matters.

Moving the image

docker save multillm:latest -o multillm.tar docker load -i multillm.tar

Use this to bring the image to a machine without building it there.

Logs and troubleshooting

The container is unhealthy

docker compose ps docker compose logs --tail 50

It becomes healthy once the port is actually bound. If it never does, the log says why — usually a port already in use.

Port already bound

sudo lsof -i :5000

Change the host side of the mapping in the compose file, keeping the container side at 5000.

Login works, remote access does not

Two candidates: the firewall on the host, and MULTI_LLM_EXPOSE not set to 1. The first is ufw allow 5000/tcp or the equivalent.

Changes do not appear

The image embeds a built frontend. Rebuild: docker compose up --build -d. Reloading the browser is not enough.

Login loops or 401 behind a proxy

Clock skew between host and container invalidates the session cookie. Sync the time on both.

Network and firewall

Three things have to line up, and failure looks the same in all three cases.

  1. The container binds all interfaces

    MULTI_LLM_EXPOSE=1 in the compose file. Without it the port is reachable from the host only.

  2. The host publishes the port

    "5000:5000". Publishing to 127.0.0.1:5000:5000 restricts it to the host.

  3. The firewall allows it

    sudo ufw allow 5000/tcp on Ubuntu, the equivalent on macOS and Windows.

From inside another container

localhost is that container. Use host.docker.internal instead, with Expose to LAN on.

Finding your address

hostname -I # Linux ipconfig getifaddr en0 # macOS
Do not expose this to the internet

There is no TLS and no rate limiting in front of it. If the team is remote, put a reverse proxy with TLS in front — see HTTPS reverse proxy.

Backup and restore

Backing up

docker run --rm \ -v multillm-data:/data:ro \ -v "$PWD":/backup \ alpine tar czf /backup/multillm-backup-$(date +%F).tar.gz -C /data .

This contains provider keys in plain storage. Treat the file as a secret.

Restoring

docker compose down docker volume create multillm-data docker run --rm \ -v multillm-data:/data \ -v "$PWD":/backup \ alpine tar xzf /backup/multillm-backup-2026-01-15.tar.gz -C /data docker compose up -d
Stop the container first

Backing up a running container can capture a half-written file. Always stop or down before copying the volume.

Configuration only

For a settings-only restore, export the config in the web interface instead — without keys. Accounts do not come with it; see moving machines.

Security

Compared to the desktop app, the container moves the trust boundary: now several people reach it over a network.

SettingWhy
Leave MULTI_LLM_ALLOW_SIGNUP unsetOtherwise anyone who reaches the port can create an account.
Put TLS in front for remote teamsNothing in the container provides encryption.
Set MULTI_LLM_COOKIE_SECURE=1 behind HTTPSSession cookies are otherwise sent over plain HTTP.
Leave MULTI_LLM_PUBLIC_DASHBOARD unsetIt makes usage and model data readable without a key.
Restrict Docker socket accessRead access to it is effectively read access to every provider key.

What stays protected anyway

Passwords are argon2id hashes, never readable. API key comparison is constant-time. Failed logins are throttled per IP. Management routes need a confirmation header that browser JavaScript sets, so a crafted link cannot drive them.

What is not protected: traffic is unencrypted, and anyone with a valid local key can spend from every configured provider.

One key per person

Extra keys can be limited to specific models and request rates. That way you can revoke one person without touching the rest of the team.

Limits

What the container does not do, stated plainly.

LimitConsequence
No TLSPut a reverse proxy in front for anything beyond a trusted LAN.
No tray iconNo desktop window; everything is in the web interface.
No autostartNothing runs after a reboot until you start it.
Host port 5000 must be freeThe container port is fixed; only the host side can move.
Local engines must be reachable from the containerlocalhost inside the container is the container. Use host.docker.internal.
Rebuilds need the source treeThe image is built from the repository, not pulled from a registry.
This is beta

The API shape may change. Keep the volume backed up before updating — see backup.
