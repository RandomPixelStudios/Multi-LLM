Guides

Sixteen guides for the things you actually do: add a provider, cut costs, move machines, recover from a failure.

Set up a provider

One provider, one key, one working request. Repeat per service.

  1. Get the key

    From the provider's own dashboard. Keep the page open — you will need the model list later.

  2. Add it in Multi LLM

    Providers › Add provider, pick the service from the list, paste the key. The base URL and format are filled in for you.

  3. Test it

    Use the test button on the card. Success reports the latency; failure names the cause.

  4. Enable what you want

    Only enabled models receive requests. Turn on the ones you actually use — a smaller list routes faster and fails over less often.

  5. Confirm through the proxy

    Run the curl request from Verify it works using the model id from the card.

Reading a failure

The dialog saysIt means
HTTP 401 or 403The key is wrong, expired, or lacks permission for that model.
HTTP 404Wrong base URL, or the model does not exist at that provider.
TimeoutNo route to the provider — firewall, proxy, or the provider is down.
Parse errorSomething answered, but not JSON. Often a captive portal or a corporate proxy.

Local engines

A local model needs no key and no network — the most private option and the one that keeps working when the internet does not.

Ollama

Start it, then add the provider in Multi LLM:

Base URL: http://localhost:11434/v1 API key: (leave empty) Format: OpenAI

Ollama serves an OpenAI-compatible API on port 11434. Pull a model first with ollama pull llama3, then refresh in the provider editor so it appears.

LM Studio

Base URL: http://localhost:1234/v1 API key: (leave empty)

Start the local server in LM Studio before adding it. The port is 1234 unless you changed it.

vLLM

vllm serve mistral-7b --port 8000 Base URL: http://localhost:8000/v1 API key: (leave empty)

vLLM takes an explicit model name at start-up. Use exactly that name in requests, or add an alias so it reads better.

Local does not mean free

It means no per-token cost. The electricity, the hardware and the time are yours. A local model in a bundle trades quality against the cloud models — see the recipes below.

HTTPS reverse proxy

Needed only if a tool refuses plain HTTP. Caddy is the shortest configuration; nginx is the one you likely already run.

With Caddy

llm.example.com { reverse_proxy localhost:5000 }

Caddy fetches and renews a certificate on its own. The tool then uses https://llm.example.com/v1.

With nginx

server { listen 443 ssl http2; server_name llm.example.com; ssl_certificate /etc/letsencrypt/live/llm.example.com/fullchain.pem; ssl_certificate_key /etc/letsencrypt/live/llm.example.com/privkey.pem; location / { proxy_pass http://127.0.0.1:5000; proxy_http_version 1.1; proxy_set_header Host $host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; # streaming responses must not be buffered proxy_buffering off; proxy_read_timeout 600s; } }
Disable proxy buffering for streaming

proxy_buffering off is what makes streaming work. With the default on, nginx collects the whole response and your tool shows nothing until the answer is complete.

Set the secure-cookie flag

When serving over HTTPS, set MULTI_LLM_COOKIE_SECURE=1 in server mode so session cookies are not sent over plain HTTP.

Team onboarding

For a small group on one machine or a server. A checklist you can hand over as-is.

  1. Install and create the first account

    The first account is automatically the admin. It can see and manage the user list.

  2. Decide where this runs

    Someone's desktop, or a server via Docker. A desktop works for a team that sits together; a server for anyone remote.

  3. Add provider keys

    Either the admin configures all providers centrally, or each user adds their own keys. The first is easier to manage; the second keeps costs attributable.

  4. Give each member a key

    Under API › API Keys, create a separate key per person or per tool. Now you can see who did what and revoke one without disturbing the rest.

  5. Hand over the three values

    URL, key, model. Use API › Client config snippets to generate a ready-to-paste block per tool.

  6. Set the budget

    A daily limit in settings makes the usage panel warn at 80 percent. Cheap insurance against one runaway loop.

On a shared server, use server mode

Each account gets its own providers, models, usage history and port. That is what MULTI_LLM_SERVER=1 — see Docker.

Cut token costs

Two levers, in order of effect.

1. Find the expensive part

The usage panel ranks models by tokens, with cost estimates. One runaway conversation is usually most of the bill. Look there first before changing anything.

2. Compress the prompts

Settings › Token compression, strength 4 to 6. See compression for what it does and does not touch.

3. Pin cheap models to cheap work

Give a cheap model its own bundle and point a tool or a task at it explicitly, instead of letting multillm pick randomly for everything.

What does not save anything

  • Shorter max_tokens only caps a cost you were going to pay anyway. Models stop when they are done.
  • Caching identical prompts only helps if you really send identical ones.
  • Compressing code. Excluded on purpose; it would change the code.
Context is where the money goes

Long conversations re-send the whole history every turn. Starting a fresh session, or summarising the history, saves more than any setting in the app.

Compression in practice

What actually changes at each strength level on a real prompt.

Please kindly analyse the following text in detail and explain it to me. TEXT Please analyse the following text and explain it. TEXT

Level 1 to 3 removes courtesy padding. The instruction itself is intact.

def load(path): with open(path) as f: return json.load(f)

Code is never rewritten, at any level. Same for JSON, fenced blocks and anything that looks like a literal.

When to turn it off

  • Prompts where exact wording matters, for example a legal or medical question you need reproduced faithfully.
  • When you are debugging what the model actually received.
  • Short prompts — there is nothing to save.

Choosing a strategy

One question decides it: do you care more about a single good answer or about it always being available?

If you…Use
Want the best model available right nowlatency or fastest
Want predictable behaviourpriority
Want every model used fairlyround_robin
Have long conversationssticky
Are not sureweighted and star what works

Starting with weighted

Run a week, look at the usage panel, star the models you were happy with. That produces a better mix than any theoretical default, because it is based on your actual tasks.

When latency is the wrong choice

latency optimises for the average. A model that is usually fast and occasionally very slow can still be picked. If reliability matters more, priority or weighted with stars behaves better.

Bundle recipes

Four bundles worth copying. Create each one under Virtual Models › Create.

fast

Strategy fastest. Members: whichever low-latency models you have. Good for autocomplete, quick edits, anything where you would rather correct a mediocre answer than wait for a good one.

cheap

Strategy priority. Members: your smallest and cheapest model first, anything else second. This is the one to point at for bulk work.

private

Strategy round_robin. Members: local engines only. Nothing leaves the machine, which makes this the bundle for sensitive input.

balanced

Strategy weighted, best model starred. The default bundle is already this; the recipe exists so you can see the intent.

Name them for what they are

cheap and quality in the tool's model field say far more than bundle1. The name is what a user sees in a model picker.

Bundle tiers

When one bundle cannot serve everything, split by quality and point each task at its tier.

  1. Group your models by tier

    Frontier, mid-tier, small. The names are yours; the point is that each group is a bundle.

  2. Give each a strategy

    quality gets priority with the best model first. standard and draft get fastest.

  3. Map tasks to tiers

    Code completion to draft, everyday chat to standard, hard problems to quality. The tier names in your tool's model field are the only thing that changes.

  4. Adjust as you learn

    If a tier is slower or more expensive than expected, change the strategy rather than moving models around.

Migrating from direct use

If you currently call providers directly, the change is mechanical.

  1. Install and add your providers

    Add what you already have configured, with the same keys.

  2. Swap the base URL

    Every tool: https://api.openai.com/v1 becomes http://localhost:5000/v1. Nothing else changes at first.

  3. Swap the key

    Use your local key. Provider keys stay behind the proxy — that is the point.

  4. Keep using the same model names

    Exact ids work unchanged, so this step is behaviour-preserving. Move to multillm only once you trust it.

  5. Then start routing

    Swap in a bundle name where you want automatic choice. Keep the explicit names where you want control.

Roll back any time

Point the base URL back at the provider and put the provider key in again. Nothing was migrated, so nothing needs migrating back.

Troubleshooting

Work in this order. It goes from the cheap check to the invasive one.

1. Is the proxy running?

The status line at the top of the window. Grey means stopped; red carries a message. curl http://localhost:5000/v1/models is the same check from outside.

2. Does the provider work?

Test button on the provider card. This isolates the problem to one side: the proxy or the provider.

3. Is the key right in the tool?

Copy it again from API › API Keys. A key regenerated earlier has already stopped working.

4. Is the base URL field name right?

Tools disagree about the name. See the field name table. An unrecognised field is silently ignored and the tool talks to the real provider.

5. Is the model enabled?

The card shows enabled / total. All models configured and none enabled is a frequent cause.

6. Read the error text

ErrorCauseFix
connection refusedNothing is listeningStart the proxy; check the port
invalid_api_keyWrong key for this proxyCopy the local key again
model does not exist or is not enabledNot configured, or switched offEnable it, or use another name
HTTP 401 upstreamProvider rejected the keyProvider dashboard → regenerate
Empty choices arrayResponse filtered out by safetyRephrase; the provider declined
Works in curl, not in the toolField name or /v1 suffixCheck the table in step 4

7. Still stuck

Settings › Export usage gives you the request history to attach to a bug report. Never export config with keys for this purpose.

Security

The threat model

Multi LLM holds your provider keys. The realistic risks are: someone else using your proxy, and a provider key leaking out of the app.

Keep it on localhost

The default. Anyone who reaches your proxy with your key spends your money. Expose to LAN only on a network you control.

Separate keys per tool and per person

Extra keys can be limited to specific models and to requests per minute. One key per tool means you can revoke a single integration without breaking everything.

Accounts are local

Passwords are stored as argon2id hashes, not readable text. Comparison takes the same time regardless of how much matches, so a wrong key cannot be found by timing. Failed logins are throttled per IP.

Do not export config with keys

Unless the destination is entirely yours. The file is plain text and contains real credentials.

Public networks

On a shared or untrusted network, expose nothing. Use a tunnel, or run locally. Anything that can reach the port can spend your money.

Updates

Multi LLM never installs itself. The update check only fetches a version file; downloading is always your decision.

Backup

Three things are worth keeping: your configuration, your usage history, and your accounts.

Configuration

Settings › Data › Export config, keys excluded. That file is the whole setup minus the secrets, and it is what you restore on a new machine.

Usage history

Export usage for accounting. It is not part of the configuration export.

Accounts and keys

These live only in your profile directory and are not covered by the config export. Copy the directory itself, while the app is closed.

Where it is

Your user profile directory, with one folder per user. Exact paths per platform are in the data section.

Back up before updating

A beta can change its settings format. A config export takes ten seconds and saves the session.

Sharing with a team

Two approaches, depending on whether members bring their own keys.

Shared keys

The admin configures providers once. Everyone uses the same setup, and the cost is shared. Simple, and you cannot attribute usage to a person without giving each one a key.

Per-member keys

Each member adds their own providers. Costs are theirs, and you cannot see them. The right choice when people pay for their own accounts.

Handing over a setup

  1. Export a config with keys excluded.
  2. Send the file, plus the page for their tool.
  3. They import it, then add their own keys.
  4. Give each member their own local key under API › API Keys.

Setting the ground rules

  • What the local key may be used for, and where it may be pasted.
  • Whether Expose to LAN is allowed, and on which networks.
  • Who to ask when a provider is down.

Updating

Check, then install manually

Settings › App › Check for updates reports a new version and gives you the link. Download the package for the platform, install over the old version, restart.

Before you update

  1. Export your config, without keys.
  2. Note your version, in case you need to go back.

What changes between versions

Beta software means the settings format can change. An import that looks wrong is usually a renamed field, not lost data — check the release notes first.

Going back

Install the older package over the newer one. Your configuration lives in your profile and is only read by the app, so an older build finds it again. Export first regardless.

Update checks and privacy

One request to GitHub for a version file, no identifying data. Switch it off in settings to make no outbound request at all.

Moving machines

  1. On the old machine

    Export config without keys, and note your version.

  2. Install on the new one

    Same or newer version. Start it once so the profile directory exists, then quit.

  3. Import

    Settings › Data › Import config. The same import that reads it on the old machine restores it here.

  4. Re-enter provider keys

    Deliberately not in the export. Copy them from the providers' own dashboards.

  5. Re-point your tools

    Same URL if the port matches, otherwise the new one. Nothing else changes.

Accounts need the profile folder

Config import does not bring accounts across. On the new machine, create the first account again. For several users, copy the profile directory with the app closed.
